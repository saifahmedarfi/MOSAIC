# Phase 2 — Metric Sensitivity: Design

**Status:** design, awaiting approval. Nothing is built until it is approved.
**Gated on:** Phase 1 verdict `NULL` (`Phase 1/phase1_verdict.json`), Phase 0 verdict `PARTIAL`.
**Deliverable:** `Phase 2/landscape_phase2.ipynb` plus a frozen pre-registration, built the way
Phases 0 and 1 were.

---

## 1. Intent, and why this is the right Phase 2

Phase 1 returned `NULL`: the landscape-conditional exploration premise is dead at a 1000-call
budget. Its pre-registration's consequence clause forecloses the controller permanently at
that budget, and this design does not re-open it. Phase 2 tests a different hypothesis, with
its own pre-registration, and it does not re-litigate any Phase 0 or Phase 1 quantity.

The reason to test *this* hypothesis next comes out of Phase 1's own numbers. Across all nine
arms (3 backbones × 3 settings) on 15 held-out oracles, the total spread in AUC-top-10 was
**0.0119**, against a median within-cell seed SD of **0.0063**. The three backbones finished
within **0.0034** of each other. Phase 0, on 8 oracles, had put them 0.0477 apart — so even
the method-level ordering did not replicate.

Two readings fit that:

1. **The methods are genuinely equivalent** at this budget. Nothing to find.
2. **The measurement is saturated.** AUC-top-10 on scalarized MPO oracles at 1000 calls
   compresses whatever differences exist into the seed noise.

Phase 1 cannot distinguish these, because it only ever used one metric. Distinguishing them is
worth doing, and it is the parent proposal's central claim: §1 and §3 argue that the field
lacks fair evaluation frameworks and that "multi-objective optimization is frequently
oversimplified through weighted scoring functions that obscure real trade-offs." Phase 2 tests
that claim directly, on oracles whose scalarization is public and reproducible.

**The why, in one line:** if the conclusion depends on the metric, then the benchmark — not the
method — has been doing the deciding, and Phase 1's null is partly a measurement result.

## 2. Hypothesis

> **H:** The ranking of molecular optimization methods is an artifact of the evaluation metric.
> Scoring the same runs on the component Pareto front rather than on the scalarized oracle
> changes which method wins.

Three things make this falsifiable rather than rhetorical: the component decomposition is
verified against the oracle itself rather than asserted (§5), the hypervolume reference point
is frozen before any run (§5), and the ranking change must replicate under resampling (§6),
which is the requirement whose absence made Phase 0's Criterion A unsound.

## 3. Goals, non-goals, anti-goals

**Goals**

- G1. Decide, by a frozen rule, whether method ranking is metric-dependent.
- G2. Measure what scalarization discards: the fraction of Pareto-optimal molecules that the
  top-10 scalar view cannot see.
- G3. Establish whether *any* metric distinguishes these three backbones at 1000 calls, which
  determines how Phase 1's null should be read.
- G4. Persist full molecule populations, so that every later phase's re-analysis is free.

**Non-goals**

- Building a Pareto optimizer. Phase 2 changes the *scoring*, not the search. A new optimizer
  is a separate hypothesis and a separate phase.
- Re-testing landscape dependence under any name, at any budget.
- New backbones, new representations, quantum components, or docking.

**Anti-goals** — outcomes that would make this a failure even if the code ran correctly

- A1. Any verdict that depends on a quantity chosen after a result was seen. In particular the
  hypervolume reference point, the component set, the primary metric pair, and the oracle
  exclusion rule are all frozen in §5–§6 before the sweep.
- A2. A component decomposition that is plausible but wrong. An unverified decomposition would
  make every multi-objective number in the phase meaningless while looking fine. §5's
  reproduction gate exists only to prevent this.
- A3. Reporting "inconclusive." Every branch of §6 is a claim.

## 5. What gets built, and the four gates that make it trustworthy

Four things must pass before the verdict means anything, and each one halts the phase rather than
degrading quietly: the **reproduction gate** (§5.1, is the decomposition right), the **gate on the
gate** (§5.1, could the probe set have detected a wrong one), the **power gate** (§5.3.1, is any
verdict reachable), and the **cross-phase reproducibility gate** (§8 L8, do Phase 1's overlapping
cells still reproduce).

### 5.1 Component decomposition, verified not asserted

All nine candidate oracles are **unweighted geometric means** of modifier-normalized components
— Tanimoto similarity to a fixed reference molecule, plus RDKit descriptors wrapped in Gaussian,
MinGaussian, MaxGaussian or ClippedScore modifiers. This was verified against GuacaMol's
published source rather than assumed; the per-oracle component lists, modifier parameters and
reference SMILES are recorded in the pre-registration.

Phase 2 **reimplements** each component explicitly in `src/phase2_components.py`. It does **not**
introspect TDC's internals, which are not a stable interface.

**Component granularity is the top-level scoring function as GuacaMol composes it.** Two
consequences, both frozen:

- `sitagliptin_mpo` and `zaleplon_mpo` carry an isomer sub-score that is itself a mean over
  per-element Gaussians. That is **one** component, not one per element — it is a single scoring
  function in GuacaMol's own composition. So component counts are 2–4, never 8+.
- Integer-valued descriptors are admissible objectives (`num_rings`, `num_aromatic_rings`,
  fluorine count), because the modifier maps each to continuous [0,1] before aggregation.

**The aggregation function is frozen as a per-oracle mapping**, every entry set to `geometric`.
Recording it as a dict rather than a single function matters: if TDC's reimplementation diverges
from GuacaMol for any oracle, that oracle fails the gate below and is excluded with its observed
deviation recorded, which reads correctly as a spec divergence rather than as a bug in our
decomposition.

**The reproduction gate.** For each candidate oracle, Phase 2 scores a frozen probe set through
both paths and requires

```
max | gmean(our_components(smi)) - tdc_oracle(smi) | <= 1e-6
```

**The probe set must be able to fail.** A geometric mean is zero whenever any component is zero,
and Phase 1 measured prior-sample reward means of 0.06–0.23 on exactly these oracles. A probe
set drawn from the ChEMBL prior would therefore be mostly 0-vs-0 agreement: it would pass while
proving nothing, which is anti-goal A2 wearing a passing badge. The frozen probe set is
constructed per oracle, deterministically, and committed:

- the oracle's own reference molecule(s) — by construction a maximal or near-maximal scorer;
- systematic single-edit neighbours of the reference, to sweep each component through its range;
- a fixed pseudo-random sample from the ChEMBL prior, for the low end.

**A gate on the gate.** The verification is only credited if the probe set actually exercises the
components: each component's observed range across the probe set must be ≥ 0.5, and ≥ 20% of
probe molecules must have a non-zero geometric mean. If either fails, the probe set — not the
decomposition — is what failed, and the phase halts rather than recording a vacuous pass.

The tolerance, the probe set, the per-oracle aggregation mapping, the range requirements and the
exclusion rule are all frozen in the pre-registration before any run. The gate executes in the
notebook **before the sweep is launched**, and the sweep refuses to start if fewer than 5 oracles
survive.

This mirrors Phase 0's AUC reimplementation, which was verified to 1e-12 against the published
function rather than trusted.

**A trap worth recording, found during design.** GuacaMol defines two different functions both
named "Ranolazine MPO": `ranolazine_mpo` (geometric mean, 4 components) and
`start_pop_ranolazine` (arithmetic mean, different components). Phase 2 targets the former. If
TDC bound the latter, a hand-written reimplementation would disagree silently — the gate is what
turns that into a recorded exclusion instead of a wrong number.

### 5.2 Metrics

Computed post-hoc from each run's persisted population. All are free — no oracle calls.

| Metric | Definition | Role |
|---|---|---|
| `auc_top10` | PMO's AUC-top-10 integral, `prev = 0` ramp-in | the Phase 0/1 metric; one half of the primary pair |
| `hypervolume` | HV of the run's component-space Pareto front, reference point the **origin** | the other half of the primary pair |
| `front_size` | number of non-dominated molecules in the population | secondary |
| `front_coverage` | fraction of the population that is non-dominated | secondary |
| `novelty` | fraction of the top-100 with Tanimoto < 0.4 to the oracle's reference molecule(s) | secondary |
| `diversity` | mean pairwise Tanimoto distance within the top-100 | secondary |
| `scalarization_loss` | fraction of Pareto-optimal molecules whose scalar score falls below the run's top-10 threshold | **G2**; descriptive, not a test |

**The reference point is the origin** (`0` in every component dimension). This is not a choice
made to suit the data: every GuacaMol component is mapped to [0,1] by its modifier, with higher
always better — including `osimertinib_mpo`'s "but not too similar" component, which is a
MinGaussian precisely so that excess similarity scores *worse*. The origin is therefore the
natural nadir, hypervolume lands in [0,1], and no degree of freedom is left for tuning it after
a result is seen.

### 5.2.1 The common unit — how every metric is aggregated across oracles

Raw hypervolume is not comparable across oracles, because the surviving set spans **2 to 4
components** (`amlodipine`, `perindopril`, `zaleplon`, `median1`, `median2` have 2; `fexofenadine`
3; `osimertinib`, `ranolazine`, `sitagliptin` 4). Averaging raw HV across them would be
meaningless. Every metric is therefore aggregated in **units of that oracle's own seed noise**:

```
z(m, o, b) = [ X(m, o, b) - mean_b' X(m, o, b') ] / SD_pool(m, o)
score(m, b) = mean over surviving oracles o of z(m, o, b)
```

where `X(m,o,b)` is the mean of metric `m` over that cell's seeds, and `SD_pool(m,o)` is the
within-cell seed SD **pooled across the three backbones** within oracle `o`.

Three things this buys, all of which the design previously lacked:

1. It makes cross-oracle aggregation legitimate — `z` is dimensionless, so a 2-component and a
   4-component oracle contribute on the same scale, and L2 is satisfied rather than merely
   acknowledged.
2. It treats `auc_top10` and `hypervolume` **identically**, which the primary comparison
   requires in order to be fair.
3. It gives Criterion C its unit for free: "the gap exceeds the noise floor" becomes
   "`score` difference > 1.0", with no choice left between median, mean and max SD. Pooling
   within oracle is the standard estimator and removes the 2× ambiguity that Phase 1's
   median-0.0063-vs-mean-0.0116 spread would otherwise have introduced.

**The bootstrap resamples oracles once per draw, shared across all three backbones**, then
resamples seeds independently within each selected cell. This is essential and is *not* what
`phase1_stats.flip_pairs` does: Phase 1 drew each cluster independently, which is correct for a
cluster-pair contrast but would be wrong here. Phase 1 measured an AUC SD of 0.229 *across
oracles* — if each backbone received its own oracle resample, that main effect would not cancel,
every draw's argmax would be close to a coin flip, and Criterion 0 would fail mechanically for
every metric regardless of the truth. `BENCHMARK-INSENSITIVE` would then be an artifact of the
resampling scheme rather than a finding.

### 5.3 The grid

| | |
|---|---|
| Oracles | the ≤ 9 that survive §5.1: `amlodipine_mpo`, `fexofenadine_mpo`, `osimertinib_mpo`, `perindopril_mpo`, `ranolazine_mpo`, `sitagliptin_mpo`, `zaleplon_mpo`, `median1`, `median2` |
| Backbones | `reinvent`, `augmented_memory`, `graph_ga` — unchanged, no new models |
| Setting | `explore_mid` for all three |
| Seeds | **chosen by the power gate below, from {5, 10, 15}, before the pre-registration is frozen** |
| Total | 9 × 3 × n_seeds = 135 / 270 / 405 runs |
| Estimated wall clock | ~1 h / ~2 h / ~3 h at 12 workers (Phase 1 measured 301.9 s/run mean, 11.8× speedup) |

**Why the setting dimension is gone.** Phase 1 settled it: setting means were 0.4109 / 0.4120 /
0.4125, a spread of 0.0016 against a seed SD of 0.0063. Carrying three settings would spend 3×
the compute to re-measure a known null. `explore_mid` is used for all three backbones rather
than Phase 1's per-backbone best, because that best was selected in-sample on Phase 1's own
oracles and importing it would import a selection this phase would then have to defend.

### 5.3.1 The power gate — and why it runs before the freeze, not after

Phase 1's single worst defect was a frozen threshold that **no data could have met**
(`min_pairs = 2` against a confirmation set admitting at most 1 testable pair), discovered only
afterwards by planting a noiseless effect. Phase 2 will not repeat that by accident, because the
risk here is concrete and quantified: Phase 1 measured the three backbones within **0.0034** AUC
of each other against a median within-cell seed SD of **0.0063**. On those numbers a 95% argmax
replication bar at 9 oracles may be unreachable for `auc_top10`, which would make
`BENCHMARK-INSENSITIVE` close to pre-determined.

So before `preregistration_phase2.json` is written, a pure simulation — no Phase 2 data, no new
runs — uses Phase 1's **measured** per-oracle means and seed SDs to answer: at 9 oracles and
n ∈ {5, 10, 15} seeds, with what probability does each verdict branch fire under (a) a planted
null, (b) a planted 1-noise-SD metric disagreement, (c) a planted 2-SD disagreement?

It then does two things:

1. **Picks the seed count**: the smallest n in {5, 10, 15} that reaches ≥ 80% power to detect a
   1-SD disagreement. That number is frozen, and the sweep runs exactly it.
2. **Stops the phase if nothing is reachable.** If no n in {5, 10, 15} makes any verdict other
   than `BENCHMARK-INSENSITIVE` attainable under a planted 2-SD effect, the build **halts and
   asks** rather than freezing an unsatisfiable rule.

The legitimacy line, stated plainly because it is the whole point: choosing the replication bar
and the seed count from a simulation driven by **Phase 0/1 data, before any Phase 2 run exists**,
is pre-registration working as intended. Changing either after seeing Phase 2 data would be
forbidden by §6 and by the project's standing rules. The gate's output is committed alongside
the pre-registration so the ordering is verifiable from timestamps, as in both prior phases.

**There is no result-triggered seed extension.** An earlier draft of this design allowed
extending to 8 seeds "if Criterion 0 comes back marginal." That is optional stopping — a
sample-size increase triggered by a result — and Phase 1's own pre-registration prohibits
running more seeds and reporting a favourable subset. The clause is deleted. The seed count is
decided once, by the gate, before the freeze.

### 5.4 Persistence — the Phase 1 defect, fixed

Phase 1's `execute_run1` built `score_trace` from `orc.mol_buffer` but kept only
`(score, call_index)`, discarding the SMILES keys. Only `top10_smiles` reached disk, so its 405
runs hold 4,050 molecules rather than 405,000, and no population-level re-analysis of Phase 1 is
possible.

`execute_run2` persists the **full buffer** as `(smiles, score, call_index)` triples. 135 runs ×
1000 molecules ≈ 135k rows, roughly 10–15 MB gzipped. Component vectors are *not* persisted —
they are recomputed from SMILES, which is free and keeps the records independent of
`phase2_components.py`'s version.

## 6. The frozen decision rule

Four criteria. Criterion 0 is a precondition; A and C decide the verdict; B is reported.

Throughout, "the winner under metric `m`" means **`argmax_b score(m, b)`** from §5.2.1 — the
argmax, not the full permutation. The distinction matters at a 95% bar: a full 3-element
permutation has chance level 1/6, an argmax 1/3, and the two bars are far apart. Criterion A is
an argmax comparison, so Criterion 0 is defined on the argmax too.

Every replication figure below comes from 10,000 hierarchical bootstrap draws with the winner
**re-selected inside each draw**, and with oracles resampled once per draw shared across
backbones (§5.2.1). Re-selection is Phase 1's correction to Phase 0: freezing the argmax before
resampling confirms ~4 flips per 40 on pure noise, and re-selecting returns 0.

**Criterion 0 — is there anything to rank?**
Quantified over **the primary pair only** — `auc_top10` and `hypervolume`. A metric has a stable
winner iff its argmax replicates in ≥ 95% of draws. Three states, all reachable:

- **Neither** has a stable winner → `BENCHMARK-INSENSITIVE`. A and C are computed and reported
  but cannot pass.
- **Exactly one** has a stable winner → the two metrics disagree about whether there is anything
  to see at all. That is metric dependence in its strongest form, and it routes to Criterion C
  for magnitude rather than to Criterion A, which needs two argmaxes to compare.
- **Both** have stable winners → Criterion A applies as written.

The five secondary metrics are **not** part of Criterion 0. An earlier draft quantified it over
all seven, which produced a false branch: if `front_size` had a stable winner while neither
member of the primary pair did, the table returned `METRIC-ROBUST`, whose stated meaning —
"a ranking exists and survives the change of metric" — would have been flatly untrue.

**Criterion A — primary, one pre-specified pair.**
Passes iff `argmax_b score(auc_top10, b) ≠ argmax_b score(hypervolume, b)` **and** that
disagreement replicates in ≥ 95% of draws, both argmaxes re-selected per draw. α = 0.05. A single
pre-specified pair owes no multiplicity correction — the logic that let Phase 1's Criterion B
carry one directional primary.

**Criterion B — secondary metrics, reported, not verdict-bearing.**
For each of the **four** secondaries — `front_size`, `front_coverage`, `novelty`, `diversity`;
the §5.2 table's other three rows are the two primary-pair members and `scalarization_loss`,
which is Criterion G2's descriptive measurement — the statistic is the **fraction of surviving oracles whose
within-oracle winner differs from `auc_top10`'s within-oracle winner**, with a hierarchical
bootstrap CI. Benjamini–Hochberg at q = 0.05 against the null that the fraction equals the
2/3 expected when winners are unrelated. Degenerate metrics (no finite variation) are excluded
**before** correction and named, so they cannot consume FDR budget silently — Phase 1 lost four
features exactly this way and the handling is inherited.

> Kendall τ was the original choice here and it was **arithmetically incapable of passing**.
> With 3 backbones a ranking has 3 elements, so τ ∈ {−1, −1/3, 1/3, 1} and the smallest
> attainable one-sided exact p is 1/6 ≈ 0.167, against a smallest BH threshold of 0.0125 across
> four metrics. No secondary could ever have been significant. This is the same class of defect
> as Phase 1's `min_pairs = 2`, caught here before the freeze rather than after the sweep. The
> per-oracle fraction above is attainable, interpretable, and reuses Criterion A's machinery.

**Criterion C — magnitude, the honesty veto.**
A winner change that is real but smaller than the noise floor is cosmetic. C passes iff

```
| score(hypervolume, b_HV) - score(hypervolume, b_AUC) | > 1.0
```

i.e. the HV-winner beats the AUC-winner, on hypervolume, by more than **one pooled seed SD** —
which is what a `score` difference of 1.0 means in the §5.2.1 unit. In the "exactly one stable
winner" state, `b_AUC` is replaced by the per-oracle AUC argmax. The noise floor is measured on
Phase 2's own runs and is never carried over from Phase 1, because the metric changed.

**Criterion G2 — scalarization loss, descriptive.**
Mean `scalarization_loss` across runs with a hierarchical bootstrap CI. Reported always, enters
no rule. It is a measurement, so it cannot come back empty, and it is the number that decides
whether a Pareto *optimizer* (§7.2) is worth building.

### Verdicts

| Verdict | Condition | Consequence |
|---|---|---|
| `METRIC-DEPENDENT` | both stable, A passes, C passes | The conclusion depends on the metric. The benchmark, not the method, has been doing the deciding. Write the evaluation-framework contribution. |
| `METRIC-RESOLVING` | exactly one stable, C passes | One metric resolves the methods and the other cannot. The benchmark's choice of metric decides whether a difference is visible at all. |
| `METRIC-ROBUST` | both stable, A fails | A winner exists and survives the change of metric. PMO's AUC-top-10 is adequate for these methods, and Phase 1's null stands as a clean refutation rather than a measurement artifact. |
| `COSMETIC` | A or the one-stable route passes, C fails | The winner moves, by less than seed noise. Report as a caution about metric choice, not as a finding. |
| `BENCHMARK-INSENSITIVE` | neither stable | No metric distinguishes these three backbones at 1000 calls. Phase 1's null is then partly a measurement-ceiling result, and the contribution is about the benchmark's resolution. |

All five are publishable claims. None is "inconclusive," which is anti-goal A3.

**The rule binds.** No criterion, α, tolerance, reference point, metric list, oracle set, seed
count or budget is adjusted to change a verdict. `phase2_verdict.py` refuses to emit a verdict
at all if the pre-registration hash or the metric-list hash fails to match the frozen file —
a `REFUSED` is the mechanism working, exactly as in Phases 0 and 1.

## 7. Approaches considered

Four candidates were on the table; the principal investigator chose the first.

1. **Metric sensitivity (chosen).** Tests the parent proposal's §3 claim, needs no new
   optimizer or oracle downloads, costs ~1 h of sweep, and reinterprets Phase 1's null instead
   of discarding it. Trade-off: it reuses oracles from Phases 0–1 (§8 L1) and it cannot show
   that a *better* method exists — only that the ranking is or isn't metric-dependent.
2. **Build a Pareto optimizer and beat scalarized MPO.** Tests §4 rather than §3 and would be a
   stronger positive result, but it needs a new optimizer rather than new scoring, and 1000
   calls is a very small budget for front-finding — it risks the same compression that produced
   Phase 1's null, with much more build risk. Deferred; Phase 2's `scalarization_loss` is the
   measurement that would tell us whether it is worth doing.
3. **Budget scaling of Phase 1's null.** Rejected in the post-Phase-1 memo. Headroom measured
   −0.004 to +0.001, so the probe cost was never the binding constraint; scaling 10× to see
   whether a measured zero becomes non-zero is ~340 GPU-hours bet against a pre-registered null.
4. **Memory-layer reuse ablation.** Narrower, and "does reuse help more on some landscapes" is
   the question Phase 1 just closed.

## 8. Known limitations, recorded in advance

- **L1. Oracle reuse.** All 9 candidate oracles appeared in Phase 0 or Phase 1. PMO contains no
  unused multi-objective oracles, so a clean held-out set does not exist. The defence is that
  the hypothesis concerns metrics rather than these oracles' landscapes — the oracles are the
  measurement surface, not the sample — but this is a real limitation and the write-up states it
  rather than hoping it goes unnoticed. External validation needs oracles from outside PMO,
  which is what §7.4's docking work was always for.
- **L2. Hypervolume is not comparable across component counts.** Every test is paired within
  oracle, and no cross-oracle HV mean is interpreted as a quantity.
- **L3. `valsartan_smarts` is a dead oracle** — all 27 Phase 1 runs scored exactly 0.0. It is
  not in Phase 2's candidate set, and that is a property of the oracle, not a filter applied
  after seeing Phase 2 data.
- **L4. The novelty check is still not done.** Whether metric-sensitivity analysis for molecular
  optimization is already published is unverified. It is a literature search, it gates the
  framing of the write-up rather than the running of the phase, and it is listed as the first
  open item.
- **L5. Phase 1's degenerate-feature defect has a cousin here.** If `phase0_lib`'s diagnostic
  path does not return what a metric needs, that metric must record NaN rather than invent a
  value, and be excluded before correction. The pattern is inherited deliberately.
- **L6. `BENCHMARK-INSENSITIVE` is the single most likely verdict**, on Phase 1's own numbers
  (backbones within 0.0034 AUC, seed SD 0.0063). §5.3.1's power gate exists to establish, before
  the freeze, whether it is *the only* reachable verdict — in which case the phase halts and
  asks rather than running a foregone conclusion. Anyone committing to this phase should expect
  "this benchmark cannot resolve these three methods at 1000 calls" as the modal outcome, and
  should regard that as the finding it is rather than as a failure.
- **L7. Execution is on the Windows machine.** The conda env `lce`, the vendored `mol_opt` clone
  and `results/` exist only there; this checkout has no `tdc` importable and no `results/`.
  Committed Phase 2 artifacts follow the repo's actual convention — `Phase 2/` — not the
  `results/`-prefixed paths that `PHASE1_RESULTS.md`'s artifact table cites.
- **L8. A free reproducibility check exists, and it is a stop condition.** Phase 1 already ran
  `explore_mid` on all 9 candidate oracles × 3 backbones × seeds 0–2, so those 81 cells overlap
  Phase 2's grid exactly. If Phase 1's run records are reachable on the execution machine, a
  pre-sweep gate asserts `auc_top10` matches run-for-run to 1e-9; a mismatch **halts** the phase,
  because a disagreement there means Phase 2's numbers are not comparable to Phase 1's and the
  cross-phase argument in §1 collapses. If the records are not reachable, that is recorded as a
  check that could not run, never as a check that passed.

## 9. What is left to the builder

- File layout mirroring Phase 1 exactly: `src/phase2_source.py` as the single editable source,
  `src/build_phase2.py` emitting `Phase 2/landscape_phase2.ipynb` + `src/phase2_lib.py` +
  `scripts/run_sweep_phase2.py`, with `# %% @notebook-only` cells excluded from the library.
  Every lesson from Phase 1's four build defects applies: constants and imports belong in the
  library, not in notebook-only cells, and `RUNS2_DIR` must be a real path outside a kernel.
- `src/phase2_stats.py`: pure numpy/scipy/pandas — hypervolume, the §5.2.1 `z`/`score`
  aggregation, the shared-oracle-resample replication bootstrap, the per-oracle winner-difference
  fraction, BH-FDR, and `phase2_verdict()` returning the five branches of §6.
- `src/phase2_components.py`: the component reimplementations and the reproduction gate. Needs
  the modifier formulas, fingerprint parameters and descriptor definitions, which live in
  GuacaMol's `score_modifier.py`, `utils/fingerprints.py`, `utils/descriptors.py` and
  `utils/chemistry.py` — the component lists and modifier parameters are in the pre-registration,
  but these four files must be read for the exact functional forms. The §5.1 gate is what proves
  the builder got them right, so a wrong reading fails loudly rather than silently.
- `scripts/phase2_power.py`: §5.3.1's simulation, run and committed **before** the
  pre-registration is frozen. Its output selects the seed count and may halt the phase.
- `tests/test_phase2.py`: the statistical layer under test on research-base. Must include a
  **pure-noise control** that returns `BENCHMARK-INSENSITIVE`, a **planted-disagreement control**
  that returns `METRIC-DEPENDENT`, a check that the shared-oracle resample is actually shared
  (an independent-resample implementation must fail it), and an assertion that Phase 0's and
  Phase 1's sources are unmodified.
- Figure set, mirroring Phase 1's eight, plus one for the power gate.
